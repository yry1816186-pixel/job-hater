# 项目治理

## 当前阶段与治理模型

本项目处于**单维护者（BDF-1）**阶段：仓库所有者（yry1816186-pixel）对方向、合并与发布拥有最终决定权；贡献者通过 Issue/PR 参与（流程见 CONTRIBUTING.md）。若未来形成稳定的多位贡献者，将在此文件记录核心团队与表决规则后再切换治理模型——切换本身按"重大变更"走下方流程。

## 决策规则

| 变更类型 | 谁决定 | 依据 |
|---|---|---|
| Bug 修复、测试补强、文档勘误 | 任何维护者可直接合并 | CI 全绿 + 描述可验证 |
| 新功能（新命令/新信源/新维度） | 仓库所有者 | 符合路线图 + 红线（CONTRIBUTING.md）+ 带测试 |
| 红线相关（采集方式、风控参数默认值、真实性校验逻辑） | 仓库所有者，且必须先在 Issue 公示 72 小时 | 反编造/反爬优先/数据本地化三条铁律不可谈判 |
| 破坏性变更（数据契约 schema_version、CLI 参数删除） | 仓库所有者 + CHANGELOG 记录 + 迁移说明 | 语义化版本 major 位递增 |

## 发布流程

1. `docs/` 下迭代报告（每轮真实改动与验证记录）归档；
2. 全部测试脚本本机跑绿；
3. 版本号按 SEMVER 递增，`CHANGELOG.md` 记录；
4. 打 tag（`vX.Y.Z`）后推送，Release 页附该版验证摘要。

## 质量基线（合并的硬条件）

- 测试全绿；新行为有用例锁死；
- 用户可见输出遵守：先结论后依据、错误带下一步指引、拦截必解释；
- 文档与实际行为一致——验证状态只有实测过才能标 ✅；
- 不新增个人事实字面量到 `core/`。

## 红线的修改

三条铁律（事实不可捏造 / 反爬优先于硬刚 / 数据不出本机）的任何放松都是"项目性质变更"：需要在此文件新增一段修订记录、递增 major 版本，并在 README 顶部声明。没有走这个流程的红线放松 PR 一律拒绝。
