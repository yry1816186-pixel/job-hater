# 性能（PERFORMANCE）

> 结论先行：20k 合成岗位规模下，批量导入 563 jobs/s、FTS 检索最差 P95 37.0 ms（全命中 19,600 行场景）、
> 全量匹配排序 431 jobs/s（含逐岗位持久化）。内置两项预算断言 PASS（ingest 吞吐、检索 P95；
> 匹配阶段仅记录未设预算），脚本退出码 0。
> **注意：合成 JD 文本显著短于真实 JD，导入吞吐不能直接外推为真实容量**——预算线以真实数据参考值
> （9,745 岗 / 123.5 s ≈ 79 jobs/s）校准，详见[与真实负载的偏差](#与真实负载的偏差)。

- 实测日期：2026-09-21
- 基准脚本：`scripts/benchmark.py`（可独立运行，零新增依赖）
- 本文档所有数字均为实测，无估算值；复现命令见下文。

## 方法论

### 基准脚本与用法

```bash
# 仓库根目录；默认 N=20000，任一预算不达标时退出码 1
python scripts/benchmark.py                        # 全量基准，结果 JSON 打到 stdout
python scripts/benchmark.py --out bench.json       # 结果同时写入文件
python scripts/benchmark.py --jobs 5000            # 快速档（外推需谨慎）
python scripts/benchmark.py --db D:/tmp/bench.db   # 保留数据库供离线检查
```

四个阶段，全部走生产代码路径（`JobService.ingest` / `JobService.search` / `MatchService.rank_jobs`）：

1. **生成合成岗位**：默认 20,000 条（`--jobs` 可调），键名与 `JobService.normalize` 接受的 raw 完全一致。
2. **批量导入计时**：按 `--batch-size`（默认 1000）分批调用 `ingest`，吞吐按 **received 口径**
   （含刻意注入的重复数据），覆盖 L2 精确去重与 L3 近似去重路径。
3. **FTS 检索计时**：6 个典型中文/混合查询，每查询 1 次预热（不计入）+ 10 次计时，输出 min/P50/P95/max。
4. **全量匹配排序计时**：构建基准画像与偏好，对全部 active 岗位运行 `rank_jobs`
   （Eligibility Gate + BM25 批量检索 + 六维评分 + 逐岗位持久化 `match_results`）。

### 计时口径（重要）

- **测稳态不测冷启动**：jieba 词典加载（首次约 1 s）与每查询的首次执行计划预热均不计入计时；
- `search()` 计时覆盖完整链路：SQL（FTS MATCH + 结构化过滤 + ORDER BY rank LIMIT 50）+ 行到模型的反序列化；
- `rank_jobs` 走生产路径，**包含**逐岗位 `persist()` 单事务写 `match_results`——这是当前实现的真实成本；
- 合成数据由 `--seed`（默认 42）驱动，`random.Random` 独立实例，同种子完全可复现。

### 性能预算（脚本内置断言，超限非零退出）

| 预算 | 阈值 | 校准依据 |
|---|---|---|
| ingest 吞吐 | ≥ 60 jobs/s | 真实数据实测约 79 jobs/s，留 ~25% 余量 |
| 检索最差 P95 | < 50 ms @20k | 交互式列表页可接受上限 |

阈值可经 `--min-ingest-rate` / `--max-search-p95-ms` 覆盖。吞吐类断言受机器噪声影响（±10% 量级），
适合本地回归与容量预警，不建议在共享 CI runner 上做硬卡点。

### 合成数据画像（seed=42，N=20000）

| 维度 | 取值 |
|---|---|
| 雇主数 | 1,000（Zipf 长尾：头部公司多岗、长尾单岗） |
| 职位族 | 16（后端/前端/算法/数据/测试/运维/产品/运营/设计/机械/职能/销售…，科技岗为主） |
| 城市 | 12，一线集中（北京/上海/深圳/杭州 合计 ~66%） |
| 描述长度 | 平均 152 字符；薪资文本 7.9% 为「面议」（检验解析降级） |
| 刻意注入重复 | L2 精确重复 400 条（2%）+ L3 近似标题 200 条（1%） |
| 标题构成 | 级别前缀（初级~资深）x 职位族 x 后缀（急招/应届/校招/远程/双休…） |

## 实测数字（N=20000）

### 环境

| 项 | 值 |
|---|---|
| OS | Windows 11（10.0.26200），AMD64 |
| CPU | Intel64 Family 6 Model 183 Stepping 1（32 逻辑核，笔记本级 Raptor Lake 平台） |
| Python | 3.12.10（CPython） |
| SQLite | 3.49.1（WAL，`synchronous=NORMAL`，`busy_timeout=10s`） |
| jieba | 0.42.1（启用；缺失时自动退回字符 bigram，检索质量略降、索引体积增大） |
| 匹配引擎 | v2.1.0；数据落盘临时目录，跑完自动清理 |

### 阶段一：批量导入（JobService.ingest，批大小 1000 x 20 批）

| 指标 | 值 |
|---|---|
| received | 20,000 |
| 入库（added） | 13,978 |
| L2 精确去重 | 400 |
| L3 近似去重（标记入库） | 5,622 |
| 拒绝 / 补全 | 0 / 0 |
| 总耗时 | 35.54 s |
| **吞吐** | **562.8 jobs/s（预算 ≥ 60，PASS）** |
| 每批耗时 | 1.34 s → 2.01 s（20 批缓升约 50%，亚线性，未见 O(n²) 拐点） |
| 落库行数 / 库体积 | 19,600 行；导入后 80.09 MB（含 WAL/SHM），全量匹配写入后最终 106.82 MB |

每批耗时的缓升来自：每批一次 O(全表) 的去重索引预装载（4 列全量 SELECT）与 L3 近似去重的
同雇主标题列表增长。20k 规模下首尾批相差约 50%，仍在同一量级。

### 阶段二：FTS 中文检索（19,600 行库，每查询 10 次计时，单位 ms）

| 查询 | 过滤 | 命中总数 | P50 | P95 | max |
|---|---|---:|---:|---:|---:|
| 产品经理 | 无 | 19,600（全命中） | 36.1 | **37.0** | 37.0 |
| python | 无 | 7,747 | 15.4 | 20.0 | 20.0 |
| 数据分析 | 无 | 7,569 | 17.2 | 19.0 | 19.0 |
| 后端开发 | 无 | 7,174 | 15.9 | 19.0 | 19.0 |
| 机器学习 | 无 | 2,749 | 9.6 | 13.9 | 13.9 |
| 算法 | 城市 IN (北京, 上海) | 599 | 5.4 | 6.9 | 6.9 |

**检索 P95 预算 < 50 ms：PASS**（最差查询 37.0 ms）。延迟与**命中集大小**近似线性而非与库总量线性
（BM25 排序 + rank 截断的成本随命中数增长）；全命中（宽泛词）是最坏场景，精确词 + 结构化过滤 < 10 ms。

### 阶段三：全量匹配排序（MatchService.rank_jobs，生产路径含逐条持久化）

| 指标 | 值 |
|---|---|
| 评估岗位 | 13,323（active；其余为过期标记行，见下文偏差说明） |
| 总耗时 | 30.89 s |
| **吞吐** | **431.3 jobs/s（2.32 ms/岗，未设预算，仅记录）** |
| eligible | 4,459（33.5%，受城市/薪资/经验 Gate 约束） |
| needs_review | 4,577（近似去重标记 + 多重不确定性） |
| match_results 写入 | 13,323 行（每岗一个独立事务） |

### 与真实负载的偏差（读数前必看）

| 偏差点 | 合成库 | 真实库 | 影响方向 |
|---|---|---|---|
| JD 文本长度 | 平均 ~152 字符 | 常见 500–2000+ 字符 | 合成 ingest/匹配显著偏快（分词、指纹、快照均随文本量增长） |
| 近重复标记率 | 28.7%（级别前缀变体与基础标题的 bigram Jaccard 恰为 0.75） | 通常个位数百分比 | 加重 ingest 的 L3 扫描成本（使读数偏保守） |
| 过期行占比 | ~32%（发布 30–59 天且带 deadline 的过半到期） | 视采集新鲜度 | 缩小 match 评估集（使匹配读数偏乐观） |

**真实数据参考值（容量规划以此为准，不以上表合成值）**：v2 导入链路实机实测
**9,745 岗位 / 123.5 s ≈ 79 jobs/s**（真实 JD 文本长度）。合成基准的 562.8 jobs/s 与之差约 7 倍，
主要归因于文本长度差；因此 ingest 预算线定在 60 jobs/s 而非合成读数附近。

## 单机资源说明

- **架构**：本地优先单机架构，SQLite 单写连接（`BEGIN IMMEDIATE`），无网络/服务依赖；
  性能上限基本取决于单核 CPU（分词/评分）与磁盘小事务延迟（WAL 提交）。
- **Windows 特有**：实时防病毒扫描会显著放大 SQLite 小事务与新建文件的开销（WAL/SHM 反复开关）；
  首次建库建议把数据目录加入杀软排除项。基准库落在临时目录（可 `--db` 指定到排除目录）。
- **jieba**：首进程加载词典约 0.9 s（有本机缓存后），常驻内存约数十 MB；缺失时自动退回 bigram 分词，
  功能不缺失但索引体积与查询质量受影响。
- **内存**：20k 规模下 ingest 预装载索引与匹配结果集均在常规定义域内（数百 MB 内核内存的笔记本可跑）；
  脚本未做内存峰值测量，超大库请自行关注。
- **数据安全**：WAL + `synchronous=NORMAL` 是性能与安全的折中——进程崩溃不损坏库，
  断电可能丢失最近提交；基准库为一次性合成数据，无此顾虑，生产数据目录同理可接受（本地缓存性质）。

## 已知上限与扩展路径

按当前 20k 实测外推的舒适区约为 **5 万岗位量级**；再往上需按下表逐项改造（均为独立可做，不改数据契约）。

| 上限点 | 触发量级（估） | 现状与证据 | 扩展路径 |
|---|---|---|---|
| ingest 每批 O(全表) 去重索引预装载 | ~50k–100k | 20 批预装载使每批约 +50% 缓升（见上表） | 加大批（5k–10k）；或预装载改增量游标（`WHERE rowid > ?`），一次性装载改为服务级常驻索引 |
| L3 近似去重内存索引 | ~100k | `near_titles` 全量驻留内存，20k 时无感 | 按雇主分桶落库（雇主哈希 → 分片索引），或限制同雇主标题候选数 |
| FTS 全命中查询延迟线性增长 | ~100k | 全命中 19,600 行 P95 37.0 ms，按命中集线性外推 100k 全命中约 200 ms | 前置结构化过滤缩小候选；产品层限制宽泛词 COUNT 展示；必要时评估 FTS5 列权重视图外的物化计数缓存 |
| rank_jobs 逐岗位 persist 单事务 | ~50k | 13,323 次独立 `BEGIN IMMEDIATE`/COMMIT 占匹配耗时的相当比例 | 改批量持久化（单事务 `executemany`）——首要优化点，预期显著降低匹配阶段耗时（需实测验证） |
| 全库 `search("", limit=N)` 装载 20k 模型对象 | ~100k | 匹配入口一次拉全量 JobPosting | 游标分片评估 + 结果合并排序；或匹配下沉 SQL 预筛（Gate 条件表达式化） |

### 大库 FTS 调优备忘（供未来参考，未实测）

当前形态已是推荐基线：FTS5 external-content（正文不重复存储，触发器维护一致性）+ 预分词空格 token +
unicode61。更大的库再考虑：检索列拆分（标题/公司/正文分列加权 bm25）、按 status 的部分索引思路、
以及把「计数 + 首页列表」合并为窗口函数单查（当前 `search` 与 `count_filtered` 两次执行同一 WHERE）。
任何调优以 `scripts/benchmark.py` 实测数字为准——没有跑分数据不合并。

## 复现

```bash
python scripts/benchmark.py --jobs 20000 --out bench-20k.json ; echo $?
# 退出码 0 = 全部预算 PASS；1 = 有预算未达标；JSON 含完整环境信息与逐次延迟
```

以上实测对应：`--jobs 20000 --batch-size 1000 --seed 42 --search-runs 10`，2026-09-21 运行于上表环境；
JSON 输出含完整环境信息与逐次延迟，可用上述命令随时复现（吞吐类数字在不同机器/负载下有 ±10% 量级波动，
计数类数字同种子完全一致）。
